# PPK V3.1：官方原币、国内报价与多市场设计

> 状态：本地正式发布完成，待服务器部署。Phase A（Schema、日度汇率快照、人民币比较值）、Phase C（首批中国大陆 / 多市场官方报价 Adapter）和 Phase D（原币主价 + 人民币参考比较价 UI）已完成代码与自动化测试；本地 V3.1 Release `20260820T134557Z-3b83d25e` 已验证 758 条模型报价、33 个套餐和 21 个自动来源。OpenAI Plus 官方页当前受 WAF 保护时，会按来源复用上一份已发布的有效数据并标记为 `stale`，不会把失败数据发布到线上。
> 前置版本：V3 已正式运行；按需模型目录来自 Models.dev，套餐来自官方自动 Adapter。
> 本文目标：补充国内厂商官方人民币报价，并让同一产品的国内/国际报价可以并存、可追溯、可比较。

## 1. 结论先行

PPK 不应把“中国用户”理解成“所有价格都必须换成人民币”。V3.1 的核心规则是：

1. 页面主价格始终显示该报价的**官方原币**；国外厂商的国际报价通常显示 `$`，国内厂商也必须按其所在官方市场实际标价显示 `¥` 或 `$`，不能按厂商国别推断币种。
2. 排序、最低价提示和模型横向比较使用统一的**参考折算货币**，固定为 `CNY`（人民币）。
3. 折算价只服务于比较，不能替代官方价格；页面必须明确标注 `≈ ¥x.xx（按 YYYY-MM-DD 参考汇率折算）`。
4. 同一厂商、同一模型在中国大陆、北京区域、国际站、新加坡等市场的报价都是独立官方报价，不互相覆盖、互相换算或做“哪个更正确”的仲裁。
5. 服务器的 VPN/IP、浏览器语言、Cookie 不能决定正式价格。**所有厂商、所有市场的 Adapter** 都必须指定目标市场和允许的官方币种；结果不符合预期即拒绝发布该来源。

这使用户能够同时看到“我实际会被官方收取什么货币”和“不同币种下大约哪个更便宜”。

## 2. 要解决的问题

当前 V3 虽已保存 `currency` 和 `region`，但仍存在以下不足：

- Models.dev 的国际按需报价与国内厂商官方人民币报价不能并存；
- 前端仍有旧的 CNY/USD 显示切换及固定汇率逻辑，容易把展示币种和厂商来源混为一谈；
- 部分官方页面会按访问 IP 返回 SGD 等当地价格，VPN 会污染采集结果；
- `ChatGPT Plus` 已自动采集，但 OpenAI 的 Pro 5x、Pro 20x、Business 等固定价格未完整进入套餐目录；
- 价格比较的“最低价”没有明确说明使用哪一种货币、哪一天的汇率；
- 国内厂商的“国内站 / 国际站 / 云市场”目前没有清晰的数据身份。

## 3. 术语与边界

| 名称 | 含义 | 例子 | 不能代替 |
|---|---|---|---|
| 厂商来源地 `provider_origin` | 厂商自身所属地区，仅用于目录信息 | `cn`、`us` | 报价币种、可购买市场 |
| 市场 `market` | 该官方报价适用的销售/服务市场 | `cn_mainland`、`global`、`sg` | 厂商来源地 |
| 调用渠道 `access_channel` | 用户从哪里购买或调用该报价 | `official_api`、`aws_bedrock` | 数据采集来源 |
| 数据来源 `source_id` | PPK 实际读取哪一份数据 | `models_dev`、`zhipu_cn_pricing` | 调用渠道 |
| 官方原币 `currency` | 官方页面标出的结算币种 | `USD`、`CNY`、`SGD` | 比较币种 |
| 参考折算币种 | 仅用于跨币种排序、比较和最低价 | 固定 `CNY`（人民币） | 官方结算币种 |

### 3.1 为什么必须区分这些字段

智谱是中国厂商，不代表其国际站一定收人民币；同样，千问北京市场即使也标 `$`，也不代表它等同于新加坡国际市场的美元报价。AWS 是美国厂商，也不代表 Bedrock 价格等同于 Anthropic 官网 API。`market` 回答“哪个官方市场”，`access_channel` 回答“通过什么路径购买”，`source_id` 回答“PPK 从哪里读取”。三者混在一个 `region` 里会导致筛选和比较都不可靠。

### 3.2 多市场报价的硬规则

**市场报价不是汇率换算结果。** `currency` 只记录官方收费币种；`market` 才决定该报价适用于哪里。即使两个市场都收美元，也必须是两条独立数据。

以下以用户提供的千问价格为设计示例；实施时必须由相应官方市场页面/API 自动验证后才可发布：

| 模型 | 官方市场 | 官方币种 | Input / 1M | Output / 1M | PPK 如何处理 |
|---|---|---|---:|---:|---|
| Qwen3.8-Max | 中国北京 | USD | $1.65 | $4.951 | 独立存为北京市场报价；仅在比较时折算为参考人民币。 |
| Qwen3.8-Max | 新加坡 International | USD | $2.00 | $6.00 | 独立存为新加坡国际市场报价；不能由北京价乘汇率得到。 |

目录中这两条报价分别列出，并清楚标明市场。比较时两个原价都按同一个日度汇率折算成人民币，方便跨市场比较；这一步不会反写或替换任何一方的官方美元价。

## 4. 用户可见规则

### 4.1 按需计费目录

默认列表按“官方报价”展示：

```text
智谱 · GLM-5
中国大陆官方 API · ¥7.00 / 1M
≈ ¥7.00 / 1M（按 2026-08-20 参考汇率折算）

千问 · Qwen3.8-Max
中国北京官方 API · $1.65 / 1M

千问 · Qwen3.8-Max
新加坡 International 官方 API · $2.00 / 1M
```

- 主价格绝不自动改成另一种货币；
- 参考折算在设置“显示比较价”开启时显示；初始桌面端可默认显示为弱化的第二行，移动端折叠到详情；
- 市场不是“国内/海外”这种模糊标签，使用 `中国北京官方`、`中国大陆官方`、`新加坡 International`、`国际官方`、`AWS Bedrock` 等明确名称；
- 价格表保留“市场”筛选；同名模型存在多市场报价时分别成行。

### 4.2 价格对比工作台

对比表每个价格单元格保留官方输入价，并在跨币种时给出参考值：

```text
Input / 1M
¥7.00
≈ ¥7.00
```

- 最低价绿色高亮只根据相同指标的 CNY 参考折算值计算；
- Tooltip/说明固定写明：`按 YYYY-MM-DD 获取的最新日度参考汇率折算为人民币，仅用于比较；最终以官方原币和结算页面为准。`；
- 同一币种对比时可以只显示原币，仍用同一排序值计算；
- 如果没有有效汇率或币种不受支持，显示 `不可折算`，该单元格不参与最低价、排序最后；绝不按 0 处理。

### 4.3 套餐目录

`ChatGPT Plus`、`Claude Pro`、`Gemini AI Pro` 等全球套餐使用 `$ / month` 很自然，也应保持官方美元展示。国内套餐继续显示 `¥ / 月`。

月费排序采用 CNY 参考折算值；卡片/表格本身仍把官方月费作为主信息。按年付费的套餐同时标注实际周期和月度参考：

```text
$240 / year
≈ ¥xx / month（按 YYYY-MM-DD 参考汇率折算，按年付）
```

不会把年付总价错误显示为月费，也不会把每席位价格说成整个团队价格。

## 5. 数据模型变更

V3.1 是一次有版本号的 Catalog Schema 升级，不复用旧 V2 兼容层。发布版本整体替换，前端只读取一个完整新 Catalog。

### 5.1 按需模型报价 `model_offers`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `offer_id` | TEXT | 是 | 稳定报价身份：`provider_id/model_id/market/access_channel/service_tier`。 |
| `provider_id` | TEXT | 是 | PPK 厂商 ID，例如 `zhipu`。 |
| `model_id` | TEXT | 是 | 厂商/来源提供的稳定模型 ID。 |
| `market` | TEXT | 是 | 明确的官方销售/服务市场，例如 `global`、`cn_beijing`、`cn_mainland`、`sg_international`。 |
| `access_channel` | TEXT | 是 | `official_api`、`aws_bedrock` 等购买/调用渠道。 |
| `service_tier` | TEXT | 是 | `standard`、`batch`、`flex` 等服务层级。 |
| `pricing_condition` | TEXT | 是 | 官方价格成立的输入区间，例如 `input_lte_128k`；无阶梯价格为 `standard`。阶梯价格必须独立保存，不能取平均值。 |
| `currency` | TEXT | 是 | 官方原币 ISO 代码，例如 `USD`、`CNY`。 |
| `price_unit` | TEXT | 是 | 当前统一 `per_1m_tokens`。 |
| `input_per_1m` 等 | REAL | 否 | 官方原币下的原始价格；缺失为 `null`，绝不写 0。 |
| `source_id` | TEXT | 是 | `models_dev` 或具体官方 Adapter ID。 |
| `source_url` | TEXT | 是 | 官方页面/API 或 Models.dev 记录地址。 |
| `source_fetched_at` | TEXT | 是 | PPK 获取该价格的时间。 |
| `comparison_currency` | TEXT | 是 | 固定 `CNY`，只用于排序和跨币种比较。 |
| `comparison_fx_rate` | REAL | 否 | 从官方原币折算到 CNY 的日度快照汇率；CNY 为 1。 |
| `comparison_fx_date` | TEXT | 否 | 本次发布所使用的日度汇率参考日期，前端必须可见。 |
| `comparison_input_per_1m` 等 | REAL | 否 | 用于排序/比较的 CNY 折算值；原价缺失或无法折算时为空。 |

`comparison_*` 是发布时确定的可复现派生数据，不是新的官方价格。历史 Release 能准确说明当时的排序为何如此。对于阶梯报价，`offer_id` 额外包含 `pricing_condition`，因此同一模型的不同输入区间会分别列出和比较。

### 5.2 套餐 `plans`

保留 V3 中已有的 `plan_category`、`billing_type`、`price_amount`、`currency`、`billing_cadence`，新增：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `market` | TEXT | 是 | 套餐目标市场；全球美元套餐为 `global`。 |
| `seat_type` | TEXT | 否 | `individual`、`standard_seat`、`codex_seat` 等；没有座位概念则为空。 |
| `minimum_seats` | INTEGER | 否 | 官方规定最低购买人数；个人套餐为空。 |
| `price_status` | TEXT | 是 | `priced`、`free`、`contact_sales`、`usage_based`。 |
| `comparison_currency` | TEXT | 否 | 固定为 `CNY`；无法折算时为空。 |
| `comparison_monthly_amount` | REAL | 否 | 每月、每用户（月）或固定周期的 CNY 参考折算价，必须搭配 `price_scope` 阅读。 |
| `price_scope` | TEXT | 是 | `per_account`、`per_user`、`per_seat`、`usage_based`。 |

`price_status = contact_sales` 或 `usage_based` 的产品可以进入目录说明能力和计费性质，但不能进入“月费从低到高”排序或首页价格卡。

### 5.3 汇率快照 `fx_snapshots`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `fx_snapshot_id` | TEXT | 是 | 本次汇率快照 ID。 |
| `base_currency` | TEXT | 是 | 固定 `CNY`。 |
| `rates_json` | TEXT | 是 | 每种原币到 CNY 的汇率。 |
| `source_url` | TEXT | 是 | 单一汇率数据来源 URL。 |
| `published_date` | TEXT | 是 | 来源公布的参考日期。 |
| `fetched_at` | TEXT | 是 | PPK 获取时间。 |
| `checksum` | TEXT | 是 | 原始汇率内容校验和。 |

推荐使用单一、公开、可留档的**日度**参考汇率源；每次 Pipeline 发布前重新获取当天可获得的最新日度汇率并保存快照，绝不使用硬编码固定汇率。实施前需做一次可用性审计，确认其稳定覆盖 `USD`、`CNY`、`SGD` 等已用币种。不会通过多个汇率源仲裁，也不使用用户浏览器实时汇率。

外汇参考源在周末、节假日可能只发布最近一个工作日的日度价格。因此前端不应笼统写“实时汇率”，而应展示快照的实际日期，例如“按 2026-08-20 参考汇率折算”。如果当天没有可用的新快照，Pipeline 不发布新的跨币种比较结果。

## 6. 数据源策略

### 6.1 国际按需报价

继续由 Models.dev 作为唯一国际模型目录来源，导入后明确标为：

```text
market = global
source_id = models_dev
currency = USD（仅接受 Models.dev 实际提供的 USD 记录）
```

Models.dev 是数据来源，不应被误标为“官方 API 渠道”。`access_channel` 仅在上游信息足够明确时写入，例如 `official_api` 或 `aws_bedrock`；无法确定时写 `unspecified_endpoint`，前端显示“国际 Endpoint”，不伪称官方直销。

### 6.2 国内厂商的官方多市场报价

每个国内厂商按**官方市场页面**新增独立、只读 Adapter。Adapter 必须产出其实际 `market` 与 `currency`，例如 `cn_beijing + USD`、`cn_mainland + CNY` 或 `sg_international + USD`；不能预设“国内厂商必然人民币报价”。`cn_beijing + USD` 仍是北京市场报价，不因币种为美元被归并为 `global`。每个市场报价都与 Models.dev 的全球记录以及同厂商其他市场记录共存。

第一批优先顺序按“公开、稳定、可自动验证”的条件确定：

1. 智谱；
2. 阿里通义 / 百炼；
3. DeepSeek；
4. MiniMax；
5. Kimi / Moonshot；
6. 小米；
7. 火山引擎（恢复展示前必须有稳定公开官方 CNY 来源）。

这不是承诺所有厂商一次完成。某厂商页面需要登录、验证码或只展示活动价时，不允许使用人工填价或 VPN 结果兜底；该市场报价暂不发布，并保留上一份该 Adapter 成功版本。一个厂商的某个市场抓取失败，不得把其另一市场报价复制或按汇率推导过来补位。

### 6.3 VPN 与地区化页面防护

每个官方 Adapter，以及 Models.dev 的国际目录导入，都需声明：

```text
target_market = global | cn_beijing | cn_mainland | sg_international
expected_currency = 该市场官方页面明确给出的币种
canonical_url = 固定官方地址
```

采集器使用固定的 Accept-Language、无登录 Cookie、无用户账号状态。若全球 Adapter 返回 `SGD`、`INR` 等非 USD 价格，结果视为地区化污染：本次该 Adapter 失败，不把 SGD 换算成美元后冒充全球官方 USD 价。若官方没有可稳定访问的全球 USD 页面，该报价不入库，直到找到明确的官方美元来源。

## 7. OpenAI 套餐补全

OpenAI 不应只保留 `ChatGPT Plus`。V3.1 新 OpenAI Adapter 应当以 Help Center 的稳定官方文章为优先来源，拆成下列独立产品，避免把不同额度/计费方式合并：

| 产品 ID | 官方价格 | `price_scope` | 首期是否入库 |
|---|---:|---|---|
| `openai/chatgpt/plus` | $20 / month | `per_account` | 是 |
| `openai/chatgpt/pro-5x` | $100 / month | `per_account` | 是 |
| `openai/chatgpt/pro-20x` | $200 / month | `per_account` | 是 |
| `openai/chatgpt/business-monthly` | $25 / user / month | `per_user` | 是 |
| `openai/chatgpt/business-annual` | $20 / user / month，按年结算 | `per_user` | 是 |
| `openai/chatgpt/business-codex-seat` | 无固定月费，使用 credits | `usage_based` | 是，目录说明，不参加月费排序 |
| `openai/chatgpt/enterprise` | 联系销售 | `contact_sales` | 是，目录说明，不显示虚构价格 |
| `openai/chatgpt/go` | 地区化定价 | — | 否，需先找到稳定官方 USD 资料 |

Business 标准席位最少 2 人，必须写入 `minimum_seats = 2`，并在 UI 中明确“每用户/月，不是整个团队总价”。Pro 两档分别使用 5x 和 20x 的名称；不能把二者都叫 `ChatGPT Pro` 后只留一条价格。

官方依据：ChatGPT Plus 固定为 $20/月；Pro 官方说明确认 $100 与 $200 两档及对应 5x/20x 用量；Business 官方账单文档明确月付 $25/用户、年付折算 $20/用户/月、最低 2 个标准席位，且 Codex-only seats 属于按量 credits。实施时 Adapter 仍会以实际抓到的官方正文为准，正文/字段缺失则不发布该来源。[ChatGPT Plus](https://help.openai.com/en/articles/6950777-what-is-chatgpt-plus)、[ChatGPT Pro tiers](https://help.openai.com/en/articles/9793128)、[ChatGPT Business billing](https://help.openai.com/en/articles/8792536)

## 8. 发布与失败策略

V3.1 仍坚持“整份 Catalog 原子发布”，但把来源失败分为两类：

| 情况 | 行为 |
|---|---|
| Models.dev 主目录失败或结构异常 | 整次不发布，沿用上一份完整 Release。 |
| 已正式纳入的国内官方报价 Adapter 失败 | 整次不发布，沿用上一份完整 Release。 |
| 新增 Adapter 首次接入、尚未标为正式 | 只在探针/候选报告中失败，不影响正式 Catalog。 |
| 日度汇率源无法取得本次运行可用的最新快照 | 整次不发布，沿用上一份完整 Release；不复用旧汇率生成新的比较结果。 |

一次 Release 绑定一个当日 `fx_snapshot_id`，确保页面上的“最低价”与该 Release 的参考汇率一致。汇率未能取得当天可获得的最新日度快照时，不发布新的跨币种比较值；这里仍没有字段级仲裁、价格人工覆盖或多个主源优先级。

| 页面 | 必要变化 |

| `/billing/per_token` | 用“市场”筛选替代旧的“国内/海外 = 货币”假设；排序以 CNY 比较值为准。 |
| 套餐页 | 显示 `$ / month`、`¥ / 月` 等官方格式；Business 明确每用户与最低席位；`usage_based`/`contact_sales` 不参加月费排序。 |
| About / 数据可信度 | 写明“官方原币展示；参考人民币仅用于跨币种排序与比较；不代表实际结算”，并展示汇率参考日期。 |

不增加面向用户的汇率切换器，也不在任何页面显示隐含 CNY 自动换算。用户可以直接阅读官方原价；参考价只作为数据库对比工具。

## 10. 实施阶段与验收

### Phase A：Schema 与汇率基础

- Catalog Schema 升级至 `3.1`；
- 增加市场、渠道、来源、比较值和汇率快照字段；
- 迁移现有 Models.dev 报价为 `global`；
- 完成每次发布前的日度汇率快照获取、留档与失败阻断；
- 增加原价与折算价不混写的单元测试。

### Phase B：OpenAI 完整套餐

- 将 OpenAI Adapter 从单一 Plus 扩展为 Plus、Pro 5x、Pro 20x、Business 月付/年付、Business Codex seat 和 Enterprise；
- 只使用上述官方 Help Center/定价资料；
- 验证 `per_account`、`per_user`、年付、usage-based、contact-sales 语义。

当前代码已具备上述 Adapter 与 fixture 测试；正式纳入发布前必须在部署环境执行 `python3 -m scripts.pipeline_v3.cli probe-plans`。如果 OpenAI 对无人值守请求返回 WAF/403，探针会明确失败，不能用浏览器 VPN 或记忆价格替代。

对于已经成功发布过的单一官方套餐来源，运行期遇到 WAF、网络超时或页面结构变化时，Pipeline 会仅复用该来源的上一份已发布且已校验的套餐，并在运行状态标为 `stale / last_known_good`。这不是人工填价，也不会从其他厂商或来源补值；如果该来源从未成功发布过，则本次仍会失败并保持线上 Release 不变。

首次从 3.0 升级到 3.1、或 V3 数据库可恢复重建但当前网站仍有已发布 Catalog 时，Pipeline 可从当前 `catalog.json` 中读取**同一官方来源 URL**的已发布套餐作为一次 Last Known Good 基线。成功发布第一份 3.1 Release 后，后续只依赖 V3 Release 历史；该过渡读取不跨厂商、不跨来源，也不新增或改写任何价格。

### Phase C：国内官方 CNY 按需报价

- 逐厂商完成探针、fixture、字段映射、双轨验证；
- 通过后才将 Adapter 设为正式来源；
- 每新增一个厂商都验证与其国际报价同时存在、不能互相覆盖。

首批实现包括：

- `qwen_model_studio`：解析百炼公开页中的北京、新加坡、弗吉尼亚、法兰克福和东京报价，并将不同 Token 阶梯分成独立 Offer；
- `deepseek_official_pricing`：解析中国大陆官方 API 的空闲/高峰时段报价，并将两种时段独立保存，保留缓存命中、未命中输入与输出价格。
- `kimi_official_k3`、`kimi_official_k27_code`、`kimi_official_k26`、`kimi_official_k25`：解析 Kimi 中国大陆官方 Markdown 定价表；每页均保留缓存命中、缓存未命中输入、输出和上下文，不从其他 Kimi 市场推导价格。
- `zai_global_official_pricing`：解析 Z.AI 国际站官方 USD 定价表；该报价与中国大陆智谱开放平台独立。中国大陆公开文档尚无同等完整的统一价格表，因此当前不从国际 USD 或 Models.dev 推导其大陆报价。
- `minimax_cn_official_pricing`、`minimax_global_official_pricing`：分别解析 MiniMax 中国大陆 CNY 与国际 USD 官方表，保留缓存读取/写入、输入阶梯及 Standard/Priority 接入层级；两套市场报价独立存在。

可用 `python3 -m scripts.pipeline_v3.cli probe-official-markets` 检查它们；通过后以 `run --official-markets` 生成候选 Catalog，尚未改为默认发布来源。

### Phase D：前端原币与比较价

- 删除旧的“厂商地区决定 CNY/USD”与固定汇率展示逻辑；
- 实现原币主价、CNY 参考折算价、市场筛选、最低价提示和移动端折叠；
- 验收首页、按需目录、Compare、套餐页和 About。

当前实现已完成上述前端数据契约：目录、Compare 与套餐页以官方原币为主显示，并用发布时写入的人民币参考价排序；首页价格预览已移除“全部统一人民币”的旧表述，首页 Compare 与完整 Compare 工作台同时展示官方价和弱化的 `≈ ¥` 参考价。本地 V3.1 Catalog 已发布；服务器部署后即可进入生产环境。

### 必测场景

1. OpenAI 国际报价遇到 SGD 页面时被拒绝，不变成美元发布；
2. 同一厂商同一模型的中国大陆/北京/国际市场报价可并存，即使均为 USD 也不能合并；
3. CNY 与 USD、或同币种的不同市场报价比较时，绿色最低价只按绑定的当日 FX Snapshot 计算；
4. 汇率缺失时不把价格当 0，也不高亮；
5. Business $25/用户/月不被显示为 $25/团队/月；
6. Enterprise/contact-sales 与 Codex usage-based 不进入月费排序；
7. 发布失败时线上保留前一份 Release；
8. 历史 Release 重放后仍能复现当时的比较排序。

## 11. 需要在实施前确认的产品决策

本文暂定以下选择，建议在写代码前确认：

1. **统一比较币种固定 CNY**：国际模型仍以 `$` 展示官方价；CNY 仅作为排序、最低价和横向比较的参考价。
2. **比较价显示策略**：建议桌面端默认显示弱化的 `≈ ¥` 和汇率日期，移动端放入第二行；若你希望页面更极简，也可改为默认隐藏、在 Compare 页面始终显示。
3. **全球报价口径**：只接受明确的全球/美国官方 USD 页面；不因采集服务器 VPN 落在新加坡而采用 SGD。
4. **市场定义**：第一阶段支持所有已经有稳定官方自动数据源的市场，至少包括 `global`、`cn_mainland`/`cn_beijing`，以及千问等已验证的 `sg_international`；不为没有稳定官方来源的市场预置虚构报价。
5. **汇率来源**：实施前选定一个单一公开、可留档的日度参考汇率源并写入运维文档；每个 Release 都重新获取并保存当天可获得的最新快照，它仅生成比较值，不改变任何官方价格。

## 12. 不做的事情

- 不把同厂商、同模型但不同市场的官方报价互相覆盖、复制或按汇率推导；
- 不把 VPN 看到的当地币种换算后伪装成美元官方价；
- 不通过多个价格源做字段级仲裁；
- 不做实时外汇交易、成本计算器或用户自定义汇率；
- 不为无法自动验证的国内价格恢复人工 YAML/人工填价；
- 不把 API 按需价、固定订阅价、按量 credits 和联系销售价混在同一个“月费”排序中。
